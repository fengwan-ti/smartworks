# 派工 + 报工回调 + 齐套真实库存（B 侧，2026-11-15）

> 负责人：B ｜ 关联：C 的 production/quality/inventory（已合并进 dw3）、A 的 EmployeeSkill（main）
> 结果：**报工能推进工序/工单状态；派工按员工技能自动分配；齐套改用 C 的库存台账（不再 mock）。**

## 1. 报工回调（C 的 production → B 的 planning）

C 的 `production/services.py` 已在工序开工/完工时调用 B 的
`planning.services.operation_start/complete`，本次补齐实现：

| 动作 | 行为 |
|---|---|
| `operation_start` | 工序 `pending/dispatched → in_production`；工单 `planned/released → in_production`；已完工工序重复开工报 `12017` |
| `operation_complete` | 工序 `→ completed`；还有未完工工序则工单保持 `in_production`；**全部工序完工 → 工单 `completed` 并 best-effort 通知 D 撤销未开始搬运任务** |
| 错误码 | 12018 工单不存在、12004 工序不存在、12017 状态不允许 |

实测（真实 HTTP）：

```
POST /production/work-orders/10/operations/10/start/     → 200 {"status":"in_progress"}
POST /production/work-orders/10/operations/10/complete/  → 200 {"status":"completed"}
```

## 2. 齐套检查改用真实库存（C 的 I-09）

`order.services.get_available_qty()` 从 mock 0 改成调用 C 的
`inventory.services.material_available({'material': id})`，不再复制库存逻辑；
C 模块不可用时退回 0 并在响应里说明。

响应里的 `availability_source` 现在是：`inventory（C 的 I-09 库存台账流水）`。
当前演示库原料还没有入库流水，所以 `ready=false`（这是真实结果，不是 bug）；C 灌入库后重跑齐套即可看到缺口变化。

## 3. 派工（A 的员工技能）

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/planning/work-orders/{id}/dispatch/` | 每道工序 + 候选操作工（按 `EmployeeSkill.step_type`） |
| POST | `/planning/work-orders/{id}/operations/{seq}/assign/` | `{user_id}` 指定派工；无技能报 `12025` |
| POST | `/planning/work-orders/{id}/auto-assign/` | 整单自动派工：每道工序选合格人员，优先派给当前任务最少的人 |

字段：`pl_work_order_operation.operator_user`（FK `core.User`）+ `operator`（姓名快照，列表展示用）。
工序派工后状态从 `pending → dispatched`；后续 C 的报工开工改为 `in_production`。

### 演示数据
