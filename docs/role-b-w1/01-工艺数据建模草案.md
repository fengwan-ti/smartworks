# 工艺数据建模草案 v1.0（B / W1·D1）

> 任务：W1 D1「工艺数据建模草案：工序模板字段、产品族、工艺路线三层结构」，判据「与 A 的 ER 图对齐」。
> 输入：《产品说明书 v1.2》2.3 / 5.3 / 7.2.1、《工作包 v1.1》6.1~6.3、`docs/er-v1.md` v1.0、`docs/api-contract.md` v1.0、分发包 Day 1 骨架。
> 配套文件：字段级明细见 `06-工序模板与产品族数据字典.md`；路线数据见 `02-六种零件工艺路线清单.xlsx`；换型矩阵见 `03-换型矩阵数据来源与取值口径.md`。
> 结论先行：**三层结构成立，且与 er-v1 的第 3.1 节同构**；需要 A 在 ER 侧做 6 处小修正（见 §6），不需要改任何已建表。

## 1. 范围与边界

| 做 | 不做 |
|---|---|
| process 应用的 6 张表设计：模板、路线、路线工序、BOM、BOM 明细、换型矩阵 | 不建产品主数据、物料、产品族（A 的 masterdata） |
| 与排产的接口字段（`route_step → work_order_operation`）| 不写排产算法（W3） |
| 与 D 的设备能力对接口径 | 不建设备台账、不维护设备能力数据（D） |
| W2 的落地顺序与验收点 | W1 不写代码、不建迁移 |

## 2. 设计原则（四条，决定了后面所有取舍）

| # | 原则 | 落地方式 | 不这样做会怎样 |
|---|---|---|---|
| P1 | **模板复用**：标准工序只定义一次 | `pr_process_template` 被 `pr_route_step.template_id` 引用；工时/参数允许在路线层覆盖 | 每个零件重复填 5 遍"粗车"，改一次标准工时要改 N 条路线 |
| P2 | **族继承**：族内共享路线模板 | 新产品从同族既有路线 `copy` 出新版本再微调；路线带 `family_id` 供按族筛选 | 产品族形同虚设，"新零件只配参数不改代码"落空 |
| P3 | **版本化**：路线/BOM 不可原地改生效版本 | `version` + `status`（draft/active/obsolete），同一产品仅一条 active | 已排产工单引用的路线被改，历史工单无法解释 |
| P4 | **参数动态化**：工艺参数不建列 | `key_params` / `inspection_rule` / 设备 `params` 用 JSONB | 每加一种新工艺参数就要改表、加迁移、全员 rebase |

## 3. 三层结构（与 er-v1 的对应关系）

```
第一层  pr_process_template（工序模板库）
           │ 1 : N（被引用，不复制数据）
第二层  md_product_family（产品族，A 维护）
           │ 1 : N
第三层  pr_route（路线，按产品+版本）─ 1 : N ─> pr_route_step（工序，按 seq）
                                                     │ 引用模板 or 专用工序
                                                     │ step_type / required_equipment_type
                                                     ▼
                                            排产：pl_work_order_operation（W3）
```

| 层 | er-v1 第 3.1 节的写法 | 本草案结论 | 差异 |
|---|---|---|---|
| 工序模板 | `pr_process_template`，7 个业务字段 | 同构，补 `is_active` / `remark` / 时间字段 | 新增字段 |
| 产品族 | er-v1 未列表，仅 `pr_route.family_id` 引用 | 同意：族表在 A 的 masterdata，B 只存 `family_id` | 需 A 在 ER 分组里把 ProductFamily 标注为 masterdata（er-v1 §一 已列在 masterdata 组，一致） |
| 工艺路线 | `pr_route`：id、code、product_id、version、status（3.1 未写 family_id） | 补 `family_id`（冗余，保存时校验一致） | 新增字段 |
| 路线工序 | `pr_route_step`：route_id、seq、template_id、std_hours、equipment_type、is_special | 字段名统一为 `required_equipment_type`（与模板一致）；补 `step_type` 冗余、`key_params`、`inspection_rule` | **字段改名**，需 A 登记 |
| BOM | `pr_bom` / `pr_bom_item` | 补 `code`、`loss_rate`、`is_substitute`；第一代单层 | 新增字段 |
| 换型矩阵 | `pr_changeover_matrix`：from、to、minutes | 补 `source`、`remark`、`updated_at`；唯一约束 (from,to) | 新增字段 |
| 设备能力 | er-v1 §3.6：`eq_equipment_capability`（D 写 B 读） | 同构；`/process/equipment-capabilities/` 只做只读代理 | 无 |

> 关键判定：**er-v1 的方向是对的，B 不需要推翻重来**；本草案的价值是把"待建表的几个关键字段"补成可建迁移的字段级定义，并把 3 处命名冲突钉死。

## 4. 数据从哪来、到哪去（数据流）

### 4.1 新产品导入（说明书 2.6.1 的 7 步 → 落到哪张表）

| 步骤 | 操作岗位 | 系统动作 | 落表 |
|---|---|---|---|
| 1 建档 | 工艺员 | A 侧录入产品主数据 | `md_product`（A） |
| 2 选族 | 工艺员 | 选择产品族，继承族内参考路线 | `md_product_family`（A） |
| 3 配路线 | 工艺员 | 从模板库取工序、调序、填工时与参数 | `pr_route` + `pr_route_step`（B） |
| 4 配 BOM | 工艺员 | 录入单层物料清单 | `pr_bom` + `pr_bom_item`（B） |
| 5 配要求 | 工艺员 | 工序绑定设备类型与检验要求 | `pr_route_step`（B） |
| 6 试制 | 计划员+操作工 | 下达试制工单，采集实测工时/质量 | `pl_work_order` + `pd_report_record`（B/C） |
| 7 量产 | 计划员 | 路线生效，参与排产 | `pr_route.status = active`（B） |

### 4.2 向下游提供什么（跨角色 I-05 / I-06 / I-07）

| 消费方 | 消费内容 | 接口 / 表 | 什么时候要 |
|---|---|---|---|
| C（执行与质量） | 工艺路线与工序（step_type、seq） | `GET /process/routes/{id}/`、`/routes/{id}/steps/` | W4 串联主干前 |
| C（领料） | BOM 明细（material_id、qty_per、loss_rate） | `/process/boms/{id}/items/` | W4 前 |
| D（转序搬运） | 工序 seq + 工位/设备 | `pl_work_order_operation`（W3 后） | W4 |
| A（产能看板） | 工序级计划时间与设备 | `pl_work_order_operation` | W4 |
| B 自己（排产） | 路线工时、设备类型要求、换型矩阵 | 本应用的 services | W3 |
| B 自己（齐套） | BOM + C 的库存可用量（I-09） | 跨应用读 | W3 |

### 4.3 排产时一次匹配的字段链路（W3 会用到的关键逻辑）

```
1. 取产品 6 种 → pr_route(status=active) → pr_route_step(按 seq)
2. 对每道工序：step_type + required_equipment_type
3. 查 eq_equipment_capability(step_type 匹配, 设备 status 可用) → 候选设备列表（D 的 I-11）
4. 查 pl_employee_skill（A 的 I-04）→ 该工序可操作人员
5. 查 pr_changeover_matrix(from=上一件产品, to=本产品) → 换型时间；缺失则用默认值并标记 default_used
6. 输出 pl_work_order_operation：equipment_id、operator_id、plan_start、plan_end
```

> 这条链路是 W1 建模是否正确的唯一判据：**只要 `route_step` 缺一个字段，第 2~5 步就断**。因此本草案把 `step_type`、`required_equipment_type`、`std_hours`、`seq` 定为必填。

## 5. 关键设计决策（含备选与理由）

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| D1 | 产品族表归 A 的 masterdata，B 只存 `family_id` | 在 process 建 `pr_product_family` | api-contract 的 W1 变更记录已定；族是主数据，不是工艺事务数据；B 不再重复建 |
| D2 | 路线工序的工时/参数**允许覆盖**模板值 | 只读模板值 | 同一"粗车"在齿轮轴与轴套上工时不同；覆盖字段为 null 时回落到模板，兼顾复用与灵活 |
| D3 | `seq` 从 10 起、步长 10 | 从 1 起连续 | 插入工序不必全表重排；删除后重排序号（services 负责） |
| D4 | 路线/BOM 用 `status` 版本化，active 不可物理删除 | 直接物理删除 | 工单/追溯引用历史路线，删除会让历史数据失去解释 |
| D5 | 换型矩阵按**产品对**存，不按设备类型拆分 | 产品对 × 设备类型三维 | W1 数据不具备（D 暂无按设备的实测）；W6 有实测后再扩展为三维，表结构可加 `equipment_type` 可空列，不破坏兼容 |
| D6 | BOM 第一代单层、无装配 | 多层 BOM | 《说明书》1.4.2 明确不做装配体；齐套检查只需单层 |
| D7 | `step_type` / `required_equipment_type` 用字符串枚举而非 FK 字典表 | FK 到字典表 | 与《工作包》2.5"枚举存小写字符串、在 models 定义常量类"一致；字典表由 A 的 `core_data_dict` 承担前端展示 |
| D8 | 设备能力不复制到 process，只做只读查询 | 冗余存一份快照到路线 | 设备能力变更（换主轴、加精度）应立刻影响排产，快照会过期 |

## 6. 与现有文档的对齐结果（需 A 处理的 6 处）

> 原则：《工作包》1.2 硬规则"任何接口格式改动，先改第 4 章契约再改代码"。以下都是**文档登记级**的修正，不涉及改已建表。

| # | 文档位置 | 现写法 | 建议 | 提出方 | 影响 |
|---|---|---|---|---|---|
| A1 | `api-contract.md` §六 已修正；《工作包》6.2 / 6.3 未同步 | `pr_product_family`、`/process/families/` | 《工作包》以 api-contract 为准：产品族在 masterdata；B 不建族表、不提供接口 | B | 消除两份文档冲突，避免 W2 建错表 |
| A2 | `er-v1.md` §2.4 `pr_route_step` | 字段名 `equipment_type` | 统一为 `required_equipment_type`（与 `pr_process_template` 一致） | B | 前端、排产匹配字段名统一 |
| A3 | `er-v1.md` §2.4 `pr_route` | 无 `family_id` | 补 `family_id`（冗余、校验一致） | B | 支持"按族取参考路线" |
| A4 | `er-v1.md` §五 状态值统一表 | 无路线/BOM 状态 | 补 `route.status` / `bom.status`：draft → active → obsolete | B | 前端 StatusTag 与字典需要翻译 |
| A5 | `er-v1.md` §四 命名约定 | 表名规则与短前缀不一致 | 补"应用短前缀"一段（pr / or / pl / md / in / pd / qa / eq / lg） | B | 消除 §2.3 与 er-v1 表述差异 |
| A6 | `er-v1.md` §三 3.1 | 未列 `is_active`、`source` 等新增字段 | 按 `06-工序模板与产品族数据字典.md` §2 补全 | B | ER 图与迁移字段数一致 |

> 另有 1 处**不是冲突、是缺口**：《说明书》2.2 的 8 台设备没有专用下料设备与滚齿机，而 6 条路线都以"下料"开头。W1 处理：棒料车床切断、板料加工中心铣外形、齿形加工中心铣齿；由 D 决定是否补设备，B 只改数据不改代码（见 06 §3.2 缺口提示）。
