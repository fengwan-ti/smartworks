## 第 1 章 这个系统在做什么

### 1.1 现实背景：多品种、小批量机加工车间

想象一个车间，给客户加工 6 种零件：

- 盘类：法兰盘 A、端盖 B、压盖 F
- 轴类：齿轮轴 C、轴套 D
- 板类：连接板 E

特点：

1. **品种多、批量小**：每个订单几十件，不是流水线；
2. **工艺不同**：有的要车、有的要铣、有的要滚齿、磨削；
3. **设备有限**：只有 8 台设备，磨床和滚齿机各只有 1 台；
4. **换产品要调机**：车完法兰盘再车端盖，要换夹具/调程序，这就是“换型”。

车间的核心问题：**客户下单了，什么时候能交货？先做哪个？哪台设备做？谁来做？料够不够？**

这套系统就是把这些问题用软件管起来。

### 1.2 四个人的分工

| 角色 | 负责 | 类比 |
|---|---|---|
| A | 主数据、用户、权限、菜单 | 公司的“档案室 + 门禁” |
| B（你） | 工艺、订单、计划、排产、预测 | 工厂的“工艺科 + 计划科” |
| C | 库存、生产报工、质量检验 | 车间的“仓库 + 统计员 + 质检” |
| D | 设备、AGV、物流 | 车间的“设备科 + 搬运队” |

### 1.3 一条数据流（先有个整体印象）

```
客户下订单（销售订单）
   → 计划员把它们汇总成主生产计划（MPS）
   → 按 BOM 算需要多少料（齐套检查）
   → 工艺路线告诉我们每件要经过哪些工序
   → 排产算法把工序分到设备、排到时间上（甘特图）
   → 派工把工序分给操作工
   → 工人开工/完工报工，系统记录进度
   → 设备/AGV 负责搬运，质量负责检验
   → 看板汇总所有数据
```

### 1.4 核心业务对象（先记住这 8 个词）

| 词 | 英文 | 用大白话解释 |
|---|---|---|
| 销售订单 | Sales Order | 客户要买什么、多少件、什么时候要 |
| 工艺路线 | Process Route | 这个零件按什么顺序经过哪些工序 |
| 工序 | Operation / Step | 一道加工动作，比如“粗车”“钻孔” |
| BOM | Bill of Materials | 做 1 件产品需要哪些材料、多少 |
| 换型 | Changeover | 设备从做 A 换成做 B 要花的时间（调机） |
| MPS | Master Production Schedule | 主生产计划，决定“这一周/这一个月做多少” |
| 工单 | Work Order | 真正下到车间的“生产任务单” |
| 报工 | Work Report | 工人报告“我做了多少件、几件不良” |

> **学习技巧**：每学一个表/接口，都问自己“它对应现实里的哪张纸/哪件事”。

## 第 2 章 计算机基础（前端、后端、数据库、API）

这一章是给“纯小白”补的地基。懂了的可以跳过。

### 2.1 一次点击发生了什么

你在浏览器里点“查询订单”按钮：

```
1. 浏览器（前端，Vue 写的页面）发出一个 HTTP 请求：
   GET http://localhost:8000/api/v1/order/sales-orders/?page=1
   请求头里带 Authorization: Token xxxx（证明你是谁）

2. 后端（Django）收到请求，先看 URL 找到对应的 View（视图函数/类）

3. View 调用 Service（业务逻辑）去数据库查数据

4. 数据库（SQLite）执行 SQL：SELECT * FROM or_sales_order LIMIT 10

5. 查到的“行”被 Django ORM 变成 Python 对象

6. Serializer 把对象转成 JSON 字符串

7. 后端返回：{"code":0,"message":"ok","data":{"results":[...]}}

8. 前端拿到 JSON，把数据渲染成表格/图表
```

**一句话**：前端负责“显示和交互”，后端负责“业务和计算”，数据库负责“存”，API 是它们之间的“快递单”。

### 2.2 HTTP 与 REST（接口的语法）

HTTP 方法：

| 方法 | 含义 | 项目里的例子 |
|---|---|---|
| GET | 查询 | 查订单列表 |
| POST | 新建/执行动作 | 新建订单、运行排产 |
| PATCH | 部分修改 | 改订单优先级 |
| PUT | 整体替换（项目里少用） | — |
| DELETE | 删除 | 删除一条 BOM 明细 |

状态码：`200` 成功、`201` 新建成功、`400` 参数/业务错误、`401` 没登录、`403` 没权限、`404` 找不到、`500` 服务器异常。

**REST 风格**：URL 代表“资源”，方法代表“动作”。

```
/api/v1/process/routes/          路线集合
/api/v1/process/routes/3/        3 号路线
/api/v1/process/routes/3/steps/  3 号路线的工序
```

**Token 认证**：登录接口给你一个字符串 token，之后每个请求放在请求头：

```
Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b
```

后端根据 token 找到用户，判断“你是谁、有没有权限”。

**JSON**：一种“键值对”文本格式，前后端都认识。项目的统一格式：

```json
{
  "code": 0,             // 0 = 成功，120xx = B 的业务错误
  "message": "ok",       // 给人看的中文提示
  "data": { ... }        // 真正的数据
}
```

### 2.3 数据库基础

- **表（table）**：一类数据，比如“订单表”；
- **行（row）**：一条记录，比如一张订单；
- **列（column）**：字段，比如订单号、交期；
- **主键（primary key）**：唯一标识一行，项目统一用 `id`；
- **外键（foreign key）**：指向另一张表，比如订单明细的 `order_id` 指向订单；
- **唯一约束（unique）**：不允许重复，比如同一路线里 `seq` 不能重复；
- **索引（index）**：加速查询，像书的目录；
- **事务（transaction）**：一组操作要么全成功、要么全失败（比如建订单 + 建明细）。

**SQL 和 ORM**：SQL 是直接写数据库语句；ORM 是用 Python 类操作数据库。Django 的写法：

```python
# 用 Python 查数据库，等价于 SELECT * FROM or_sales_order WHERE status='confirmed'
orders = SalesOrder.objects.filter(status='confirmed')

# 等价于 INSERT INTO ...
SalesOrder.objects.create(code='SO202611-0001', due_date=date(2026, 12, 1))
```

> 本项目演示用 SQLite（一个文件），生产环境可换 PostgreSQL；因为用 ORM，业务代码基本不用改。

### 2.5 DRF（Django REST Framework）四个概念

DRF 是 Django 上写 API 的库。

| 概念 | 作用 | 项目例子 |
|---|---|---|
| Serializer | 把模型对象 ↔ JSON，并校验入参 | 订单明细数量必须是数字 |
| ViewSet | 一组接口（增删改查） | `ProcessRouteViewSet` |
| Router | 自动把 ViewSet 映射成 URL | `/routes/`、`/routes/{id}/` |
| Action | 在 ViewSet 上加自定义动作 | `activate`、`copy`、`run` |

一个最小的 ViewSet 例子（带注释）：

```python
from rest_framework import viewsets

class ProcessRouteViewSet(viewsets.ModelViewSet):
    # 列表查询用的数据源；select_related/prefetch_related 是为了减少数据库查询次数
    queryset = ProcessRoute.objects.select_related('product').prefetch_related('steps')
    serializer_class = ProcessRouteSerializer  # 用哪个序列化器

    def perform_create(self, serializer):
        # 不直接 serializer.save()，而是调 service，保证业务规则（编码、版本、唯一性）都走 services
        serializer.instance = services.create_route(serializer.validated_data)

    @action(detail=True, methods=['post'])  # 路径变成 /routes/{id}/activate/
    def activate(self, request, pk=None):
        route = services.activate_route(self.get_object())  # 业务在 service
        return Response(ProcessRouteSerializer(route).data)
```

### 2.6 Vue 3 前端基础

Vue 是“数据驱动界面”的框架：你改数据，页面自动更新。

```vue
<template>
  <!-- 模板：写页面长什么样；{{ }} 是插值 -->
  <el-button @click="load">{{ loading ? '加载中' : '刷新' }}</el-button>
  <el-table :data="rows">...</el-table>
</template>

<script setup>
// 组合式 API：ref 定义响应式变量，改它页面会更新
import { onMounted, ref } from 'vue'
import { fetchOrders } from '@/api/order'

const rows = ref([])        // 表格数据
const loading = ref(false)  // 加载状态

  loading.value = true
  try {
    const data = await fetchOrders({ page: 1 })  // 调后端接口
    rows.value = data.results                     // 赋给表格
  } finally {
    loading.value = false

}

onMounted(load)  // 页面加载完自动调一次
</script>
```

## 第 3 章 领域知识：工艺与计划到底管什么

### 3.1 工序模板 vs 工艺路线（菜谱 vs 菜单）

- **工序模板**：一道工序的“标准做法”。例：粗车，标准工时 0.5 小时/件，需要车床。
- **工艺路线**：某个零件按顺序用哪些模板。例：法兰盘 A = 下料 → 粗车 → 精车 → 钻孔 → 检验。

用做饭类比：

- 工序模板 = “炒青菜”这道菜的标准做法；
- 工艺路线 = 一桌宴席的上菜顺序（先冷盘、再热菜……）。

为什么分开？因为很多零件会复用同一道工序（比如都要粗车），改标准工时就改模板，不用逐个路线改。

### 3.2 BOM（配方）

BOM 回答“做 1 件产品，要消耗多少材料”。

```
法兰盘 A 的 BOM：
  MT-45（45 号钢）  单件用量 2.5 kg  损耗率 5%
```

齐套检查时：

```
需要量 = 计划数量 × 单件用量 × (1 + 损耗率/100)
例：做 60 件 → 60 × 2.5 × 1.05 = 157.5 kg
```

### 3.3 换型（调机时间）

设备从做 A 换到做 B 要花的时间（换夹具、调程序、试切）。项目里有一张 6×6 的**换型矩阵**：

```
          后产品
前产品   A    B    C
A        -    15   45
B        18   -    45
C        45   45   -
```

排产时，如果一台设备上一件做的是 A、下一件做 B，就要多等 15 分钟。**换型不算在单件工时里，单独加。**

### 3.4 订单 → MPS → 工单 → 工序 → 报工

| 层级 | 谁生成 | 含义 | 例子 |
|---|---|---|---|
| 销售订单 | 销售/计划员 | 客户需求 | SO202611-0001，交期 11-30 |
| MPS | 计划员 | 一段时间内各产品做多少 | MPS202611-01：法兰盘 60、端盖 50… |
| 工单 | 排产 | 真正下到车间的任务 | WO202611-0001：法兰盘 60 件 |
| 工单工序 | 排产 | 工单拆成一道道工序 | 下料、粗车、精车… |
| 报工 | 工人 | 实际做了多少、几件不良 | 粗车完成 60 件，不良 1 件 |

### 3.5 编码规则与状态机

编码（就像身份证号，方便人看）：

| 对象 | 规则 | 例 |
|---|---|---|
| 工序模板 | PT-序号 | PT-001 |
| 工艺路线 | PR-产品编码-V版本 | PR-PF-PL-001-V1 |
| BOM | BM-产品编码-V版本 | BM-PF-PL-001-V1 |
| 销售订单 | SO年月-序号 | SO202611-0001 |
| MPS | MPS年月-序号 | MPS202611-01 |
| 工单 | WO年月-序号 | WO202611-0001 |
| 排产方案 | SP年月日-序号 | SP20261115-001 |

**状态机**：状态不能乱跳。

```
订单：草稿 → 已确认 → 已排产 → 生产中 → 已发货 → 关闭
                   ↘ 取消（草稿/已确认/已排产可以取消）

工单：草稿/已排产 → 已下达 → 生产中 → 已完工
工序：待开始 → 已派工 → 加工中 → 已完成
```

非法跳转会被拒绝（错误码 12017）。**为什么要有状态机？** 防止“已发货的订单又被排产”这种数据混乱。

### 3.6 几个重要口径

- **不占设备工序**：下料（cutting）、检验（inspection）在 8 台设备里没有对应设备，所以模板标 `is_equipment_free=True`，排产只占时间、不占设备；
- **优先级 priority**：1 最高（断料/停线）、2 当班必到、3 默认、4 可顺延、5 有空再做；
- **工位/装卸点**：D 的设备台账里每台设备绑一个工位（ST-…），工位绑一个 AGV 装卸点（N…），搬运任务用它当起终点。

## 第 4 章 算法从零讲

### 4.1 需求预测

#### 4.1.1 时间序列是什么

按时间顺序排的一串数字。比如某种零件每周的需求量：

```
第1周 31，第2周 29，第3周 26，……，第261周 51
```

我们想根据前 261 周，预测未来 8 周。

时间序列通常有三部分：

- **趋势**：整体上升/下降；
- **季节**：每年/每周重复的规律（比如年底需求高）；
- **噪声**：随机波动，无法预测。

预测模型就是在“抓趋势 + 抓季节”，剩下的噪声没办法。

#### 4.1.2 四个由浅入深的模型

**① 移动平均（MA）**

用最近 4 周的平均值当预测：

```
预测值 = (上周 + 上上周 + 上上上周 + 上上上上周) / 4
```

优点：简单、平滑噪声；缺点：跟不上趋势和季节。

**② 季节朴素（seasonal naive）**

用去年同一周当预测：

```
预测第 100 周 = 第 48 周的实际值（相差 52 周）
```

优点：如果数据有稳定年度周期，这个“笨办法”很强；缺点：完全没考虑新趋势。

**③ 指数平滑（Holt-Winters）**

给最近的数据更大权重，同时建模趋势和季节。可以理解为“会算趋势的加权平均”。

**④ SARIMA（季节性差分自回归移动平均）**

名字吓人，拆开看：

- **AR（自回归）**：用过去的**值**预测现在，比如“上周高，这周可能也高”；
- **MA（移动平均）**：用过去的**预测误差**修正；
- **I（差分）**：把数据做差（这周 - 上周），去掉趋势，让数据“平稳”；
- **S（季节）**：在季节周期（52 周）上做同样的操作。

写法 `(p,d,q)(P,D,Q,s)`：

- `p`：普通 AR 阶数；`d`：普通差分次数；`q`：普通 MA 阶数；
- `P/D/Q`：季节部分的 AR/差分/MA；`s`：季节周期（52）。

本项目用 `(1,0,0)(0,1,0,52)` + 漂移：

- 普通 AR(1)：用上一周的值；
- 普通差分 d=0；
- 季节差分 D=1：用“今年这周 - 去年这周”，去掉年度周期；
- 季节 AR/MA 都是 0（为了快）；
- 漂移（drift）：允许有长期趋势。

#### 4.1.3 怎么判断预测好不好：MAPE 和 RMSE

假设真实值 `y`，预测值 `ŷ`。

**MAPE（平均绝对百分比误差）**：

```
MAPE = 100% / n × Σ |y - ŷ| / y
```

例子：真实 100，预测 90 → 误差 10%；真实 50，预测 55 → 误差 10%。

**RMSE（均方根误差）**：

```
RMSE = sqrt( mean( (y - ŷ)² ) )
```

它对大误差惩罚更重（因为平方）。

**训练/测试切分**：不能拿全部数据训练再在同一批数据上评价（等于考前看答案）。所以用**前 253 周训练、最后 8 周测试**。

**宏均 vs 微均**：

- 宏均：每个零件先算 MAPE，再平均（每个零件权重一样）；
- 微均：所有误差加起来除以所有真实值（大销量零件权重大）。

项目用宏均，避免大销量零件掩盖小零件的问题。

#### 4.1.4 本项目结果怎么读

| 模型 | 平均 MAPE |
|---|---|
| 移动平均 | 13.7% |
| 季节朴素 | 5.04% |
| **SARIMA** | **3.66%** |

含义：SARIMA 平均误差 3.66%，比“去年同周”的 5.04% 好，比移动平均 13.7% 好很多。

**为什么 SARIMA 参数选得“不完整”？** 完整季节 MA 拟合 261 周要 60 秒/产品，答辩现场会卡；用简化配置 0.6 秒/产品，精度还更好。这是**工程取舍**，不是偷懒。

### 4.2 排产

#### 4.2.1 问题定义

已知：

- 4 张工单（每张一个产品、数量、交期）；
- 每个产品的工艺路线（工序顺序、标准工时）；
- 8 台设备，每台能做哪些工序、状态；
- 换型矩阵。

求：每道工序**哪台设备、几点开始、几点结束**。

这在运筹学里叫 **job shop scheduling**（作业车间调度），是 NP-hard 问题（规模大时很难求最优）。

#### 4.2.2 规则版（贪心）算法

我们没求解器，用规则：

1. 工单按 **交期早 → 优先级高** 排序（急的先做）；
2. 一张工单内部按工序顺序串行（粗车完才能精车）；
3. 每道工序在“能做的设备”里选**最早空出来**的那台（贪心）；
4. 如果设备上一件做的是别的产品，加换型时间；
5. 下料/检验不占设备，直接接在上一道后面。

用生活类比：银行办业务，先取号（交期早的号靠前），每个窗口叫号，客户去最早空出来的窗口。

#### 4.2.3 为什么是“贪心”而不是“最优”

- 贪心每步选当前最好，不保证全局最优；
- 但规模小、可解释、毫秒出结果；
- 真要优化，可以换遗传算法/OR-Tools，只改 `services.py`。

#### 4.2.4 关键指标

- **makespan**：从第一道工序开始到最后一道结束的总时长；
- **准时率**：计划完成时间 ≤ 交期的工单比例；
- **设备负荷**：设备忙碌时间 / 总时长；
- **换型次数**：设备切换产品的次数。

本项目：4 工单、20 工序、7 次换型、makespan 171h、准时率 100%、5 台设备。

#### 4.2.5 局限（学习时要理解）

- 连续时间，不扣午休/夜班；
- 工单内部不能并行（真实车间有时可以）；
- 用标准工时，不按设备产能差异化；
- 没考虑设备故障/急单插单（W5+ 可扩展）。

### 4.3 齐套检查

就是“物料够不够”：

```
1. 对 MPS 里每个产品，找生效 BOM；
2. 对 BOM 每行物料：
   需求 += 计划数量 × 单件用量 × (1 + 损耗率)
3. 查库存可用量；
4. 缺口 = max(需求 - 可用, 0)；
5. 全部缺口为 0 → 齐套，否则缺料。
```

这是 **MRP（物料需求计划）** 的简化版（只展开一层 BOM）。

### 4.4 敏感性分析（换型时间估错了怎么办）

D 给的换型时间是“估值”，不是实测。做法：

- 把换型时间乘 0.5 / 1.0 / 1.5，各排一次产；
- 看 makespan、准时率变化。

结果：makespan 170.5 / 171.0 / 171.5 小时，只变 ±0.3%。

结论：换型不是瓶颈，估错 ±50% 不影响排产结论；真正的瓶颈是磨削（2.5 件/h）和滚齿（1.8 件/h）。

### 4.5 派工

约束：每个人只有部分工序技能（员工技能表）。

规则：

1. 筛出有该工序技能、且启用的人；
2. 优先派给当前任务少的人（负载均衡）；
3. 任务数相同看技能等级（高级优先）。

```python
class RouteStep(models.Model):
    # 外键：属于哪条路线；CASCADE = 路线删了，工序跟着删
    route = models.ForeignKey(ProcessRoute, on_delete=models.CASCADE,
                              related_name='steps')

    # 工序顺序：10、20、30……留间隔方便插入新工序
    seq = models.PositiveIntegerField(verbose_name='工序序号')

    # 可引用工序模板；模板删了置空（SET_NULL），不删这条路线
    template = models.ForeignKey(ProcessTemplate, null=True, blank=True,
                                 on_delete=models.SET_NULL)

    # 工序类型：只能从 11 个枚举里选（StepType 来自 equipment/constants.py）
    step_type = models.CharField(max_length=32, choices=StepType.choices)

    # 单件标准工时（小时），用 Decimal 避免浮点误差
    std_hours = models.DecimalField(max_digits=8, decimal_places=3)

    # True = 下料/检验，排产不占设备
    is_equipment_free = models.BooleanField(default=False)

    class Meta:
        db_table = 'pr_route_step'  # 数据库表名
        # 同一条路线里序号不能重复
        constraints = [
            models.UniqueConstraint(fields=['route', 'seq'],
                                    name='uq_pr_route_step_route_seq'),
        ]
```

要理解的知识点：

- `ForeignKey` = 多对一关系；
- `on_delete`：CASCADE（级联删）、SET_NULL（置空）、PROTECT（禁止删）；
- `choices`：枚举，防止写错值；
- `DecimalField`：金额/数量/工时用 Decimal，不用 float（0.1+0.2 != 0.3 的坑）；
- `db_table`：表名规范（`pr_` 前缀）；
- `UniqueConstraint`：数据库层防重复。

### 5.4 服务：排产核心（`planning/services.py` 简化）

```python

    for step in route_steps(item.product):   # 按工艺路线逐道工序

        duration = max(int(item.qty * step.std_hours * 60), 1)

        if step.is_equipment_free:
            # 不占设备：接在上一道后面（没有上一道就从计划开始）
            start = prev_end or start_at
        else:
            # 1) 找能做这道工序的设备（只看 step_type，不看 params）
            pool = _equipment_pool(step.step_type)
            # 2) 选“最早空出来”的那台
            best = min(pool, key=lambda c: equipment_available.get(c.equipment_id, start_at))
            eq = best.equipment

            # 3) 换型：如果上一件是别的产品，要加换型时间
            co = _changeover_minutes(last_product.get(eq.id), item.product)

            # 4) 开始时间 = max(设备空出来的时间 + 换型, 上一道工序结束)
            start = max(equipment_available.get(eq.id, start_at)
                        + timedelta(minutes=co),
                        prev_end or start_at)

            # 5) 更新设备可用时间和设备上“最后做的产品”
            equipment_available[eq.id] = start + timedelta(minutes=duration)
            last_product[eq.id] = item.product

        prev_end = start + timedelta(minutes=duration)  # 这道工序结束
        # 写 WorkOrderOperation + SchedulePlanDetail（plan_start/end）
```

```python
    if model == 'moving_average':
```

### 5.8 前端：甘特图是怎么画的（ECharts custom series）

```js
series: [{
  type: 'custom',
  renderItem(params, api) {
    const row = api.value(0)                          // 第几行（哪张工单）
    const startPx = api.coord([api.value(1), row])    // 开始时间 → 屏幕坐标
    const endPx = api.coord([api.value(2), row])      // 结束时间 → 屏幕坐标
    const height = api.size([0, 1])[1] * 0.55         // 条的高度

    // 画一个矩形：x=开始像素，宽度=结束-开始
    return {
      type: 'rect',
      shape: {
        x: startPx[0],
        y: startPx[1] - height / 2,
        width: Math.max(endPx[0] - startPx[0], 2),
        height,
      },
      style: api.style(),   // 颜色等
    }
  },
  data,
}]
```

理解：ECharts 的坐标轴把“时间”映射成 x 像素，把“工单”映射成 y 行；每条工序数据是 `[行号, 开始时间戳, 结束时间戳]`。
