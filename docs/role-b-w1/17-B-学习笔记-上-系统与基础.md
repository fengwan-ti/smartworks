## 1. 一个订单的完整旅程（全书的线索）

先记住这个故事，后面每一章都是它的展开。

### 场景

客户“华东机械”下单：**法兰盘 A（PF-PL-001）60 件，11 月 30 日交货。**

### 第 1 步：录销售订单

- 现实：销售/计划员把客户需求录进系统；
- 系统：`or_sales_order` + `or_order_item` 两张表；
- 页面：订单与计划 → 销售订单；
- 代码：`order/services.py → create_order()`。

### 第 2 步：确认订单 → 生成 MPS

- 现实：计划员确认“这单能做”，把它汇总进本周/本月的生产计划；
- 系统：`or_mps` + `or_mps_detail`；
- 页面：主生产计划 → 从已确认订单生成；
- 代码：`order/services.py → mps_from_orders()`；
- 注意：MPS 是**按产品汇总**的（多个订单的同一产品会加在一起）。

### 第 3 步：齐套检查（料够不够）

- 现实：仓库看看 45 号钢够不够 60 件；
- 系统：按 BOM 展开成物料需求，扣库存可用量，算缺口；
- 表：`pr_bom`、`pr_bom_item`、`or_material_requirement`；
- 代码：`order/services.py → check_kit()`。

### 第 4 步：查工艺路线（怎么做）

- 现实：工艺员查这个零件的工艺卡；
- 系统：`pr_route` + `pr_route_step`（法兰盘 A 有 5 道：下料→粗车→精车→钻孔→检验）；
- 页面：工艺配置 → 工艺路线。

### 第 5 步：排产（哪台设备、几点做）

- 现实：计划员把 60 件拆到设备上，排出甘特图；
- 系统：`pl_work_order` + `pl_work_order_operation` + `pl_schedule_plan(_detail)`；
- 页面：计划与排产 → 排产与甘特图；
- 代码：`planning/services.py → run_schedule()`。

### 第 6 步：派工（谁来做）

- 现实：班长把工序分给有技能的工人；
- 系统：给 `pl_work_order_operation.operator_user` 赋值；
- 页面：甘特页 → 工单表 → 自动派工；
- 代码：`planning/services.py → auto_assign_operations()`。

### 第 7 步：搬运 + 报工（执行）

- 现实：AGV 把料从下料区搬到车床，工人开工/完工报数；
- 系统：
  - B 输出“工序间转序 leg” → D 的 `from-legs` 生成搬运任务；
  - C 的报工接口调 B 的 `operation_start/complete`，回写工序/工单状态；
- 表：D 的 `lg_transport_task`、C 的 `pd_work_report`、B 的 `pl_work_order_operation`。

### 第 8 步：看板（汇总）

- 现实：厂长看今天做了多少、有没有延迟；
- 系统：`GET /planning/dashboard/` 聚合方案 KPI、工单进度、报工良品、瓶颈、齐套；
- 页面：计划与排产 → 生产看板。

> **这就是“感知—分析—决策—执行”在一个订单上的具体样子。**

## 2. 计算机基础：网页为什么能显示数据库里的数据

这一章对应课件《02 软件开发基础》。课件讲的是“前端 + 后端 + 数据库”，我们项目是同一套思路，只是把 MySQL 换成了演示更方便的 SQLite、把 HTML/JS 换成了 Vue 3。

### 2.1 三层架构

```
┌─────────────────────────────┐
│ 前端（浏览器）              │  Vue 3 + Element Plus + ECharts
│ 负责：页面、按钮、表格、图表 │  代码：frontend/src/views/**
└──────────────┬──────────────┘
               │ HTTP 请求（JSON）
┌──────────────▼──────────────┐
│ 后端（Django + DRF）        │  负责：业务规则、计算、权限
│ View → Service → Model      │  代码：backend/apps/**
└──────────────┬──────────────┘
               │ SQL（由 ORM 生成）
┌──────────────▼──────────────┐
│ 数据库（SQLite）            │  负责：持久化保存
│ 表：pr_/or_/pl_/md_/eq_/lg_ │
└─────────────────────────────┘
```

### 2.2 一次点击的完整过程（一定要理解）

以“工艺路线页面加载列表”为例：

```
1. 你打开 http://localhost:5173/#/process/routes
2. 浏览器加载 Vue 应用，路由匹配到 RouteDesign.vue
3. 页面 mounted 时执行 loadRoutes()
4. 调用 api/process.js 的 fetchRoutes()
5. axios 发请求：
   GET http://localhost:8000/api/v1/process/routes/?page=1&page_size=50
   Header: Authorization: Token xxxx
6. Django 根据 URL 找到 urls.py → ProcessRouteViewSet
7. ViewSet 查数据库：SELECT ... FROM pr_route ...
8. Serializer 把模型对象变成 Python dict → JSON
9. 统一响应包装：{"code":0,"message":"ok","data":{"count":6,"results":[...]}}
10. axios 响应拦截器拆出 data；页面把 results 赋给表格
11. Vue 自动把表格渲染出来（你改数据，页面自己更新）
```

**记住**：前端不直接连数据库；数据库也不认识 Vue。中间靠**接口（API）**传 JSON。

### 2.3 HTTP 基础

| 概念 | 说明 | 项目里的例子 |
|---|---|---|
| URL | 资源的地址 | `/api/v1/process/routes/` |
| GET | 查 | 查路线列表 |
| POST | 新建/执行 | 新建订单、运行排产 |
| PATCH | 局部修改 | 改工序工时 |
| DELETE | 删除 | 删 BOM 明细 |
| 状态码 | 结果 | 200 成功、201 新建成功、400 业务错误、401 未登录、404 找不到 |
| Header | 请求头 | `Authorization: Token xxx` |
| Body | 请求体 | JSON 参数 |


### 2.4 数据库基础

**表、行、列**：

```
pr_process_template（工序模板表）
+----+--------+-------+---------------+-----------+
| id | code   | name  | step_type     | std_hours |
+----+--------+-------+---------------+-----------+
| 1  | PT-001 | 下料  | cutting       | 0.250     |
| 2  | PT-002 | 粗车  | rough_turning | 0.500     |
+----+--------+-------+---------------+-----------+
```

- **主键（PK）**：`id`，唯一标识一行；
- **外键（FK）**：比如 `pr_route_step.route_id` 指向 `pr_route.id`，表示“这道工序属于哪条路线”；
- **唯一约束**：`(route_id, seq)` 不能重复——同一条路线不能有两个 10 号工序；
- **索引**：像书的目录，加快“按 status 查”的速度；
- **事务**：建订单 + 建明细必须一起成功，否则回滚。

**SQL vs ORM**：

```python
# SQL 写法（了解即可）
# SELECT * FROM pr_route_step WHERE route_id = 1 ORDER BY seq;

# Django ORM 写法（项目里用这个）
steps = RouteStep.objects.filter(route_id=1).order_by('seq')

# ORM 的好处：用 Python 对象操作，换数据库（SQLite→MySQL/PostgreSQL）基本不用改业务代码
```

### 2.6 Django 项目结构（后端是怎么组织的）

```
backend/
  manage.py                 # 命令行入口（runserver / migrate / test）
  config/
    settings.py             # 数据库、时区、安装的 app 等配置
    urls.py                 # 总路由：/api/v1/process/ → apps/process/urls.py
  apps/
    process/                # 一个 app = 一个业务模块
      models.py             # 表
      services.py           # 业务逻辑（重点！）
      serializers.py        # JSON ↔ 对象、入参校验
      views.py              # 接口
      urls.py               # 路由
      filters.py            # 筛选
      migrations/           # 数据库迁移脚本
      tests/                # 测试
      management/commands/  # 自定义命令（seed_xxx 等）
    order/
    planning/
```

**请求进入后端后的顺序**：

```
urls.py（找路径） → views.py（收参数） → services.py（业务） → models.py（读写数据库）
                                   ↘ serializers.py（把结果转 JSON）
```

**为什么要有 services.py？**
课件《02 软件开发基础》讲分层思想：视图只负责“接口”，业务逻辑独立出来，便于复用和测试。B 的排产、齐套、预测都在 services 里，换一个入口（脚本、定时任务）也能调。

### 2.7 DRF：写 API 的四个零件

```python
from rest_framework import viewsets
from rest_framework.decorators import action
from rest_framework.response import Response

class ProcessRouteViewSet(viewsets.ModelViewSet):
    # ① 查询集：列表/详情默认查这些数据（select_related 减少查询次数）
    queryset = ProcessRoute.objects.select_related('product').prefetch_related('steps')

    # ② 序列化器：模型对象 ↔ JSON
    serializer_class = ProcessRouteSerializer

    # ③ 新建时走 service（不要把业务写在 view 里）
    def perform_create(self, serializer):
        serializer.instance = services.create_route(serializer.validated_data)

    # ④ 自定义动作：URL 自动变成 /routes/{id}/activate/
    @action(detail=True, methods=['post'])
    def activate(self, request, pk=None):
        route = services.activate_route(self.get_object())
        return Response(ProcessRouteSerializer(route).data)
```

DRF 的 Router 会自动生成这些 URL：

```
GET    /routes/          列表
POST   /routes/          新建
GET    /routes/{id}/     详情
PATCH  /routes/{id}/     修改
DELETE /routes/{id}/     删除
POST   /routes/{id}/activate/   自定义动作
```

### 2.8 Vue 3 前端：数据驱动页面

```vue
<template>
  <!-- 模板：页面长什么样；{{ }} 显示变量；@click 绑定点击事件 -->
  <el-table :data="rows" border>
    <el-table-column prop="code" label="路线编码" />
    <el-table-column prop="product_name" label="产品" />
  </el-table>
  <el-button @click="load">刷新</el-button>
</template>

<script setup>
import { onMounted, ref } from 'vue'
import { fetchRoutes } from '@/api/process'

// ref：响应式变量；改 rows.value，表格自动更新
const rows = ref([])

async function load() {
  const data = await fetchRoutes({ page: 1 })  // 调接口
  rows.value = data.results || []              // 赋给表格
}

onMounted(load)  // 页面加载完自动执行一次
</script>
```

核心概念：

- **组件**：一个 `.vue` 文件就是一个组件；
- **响应式**：`ref()` / `reactive()` 包起来的变量，改了页面会自动更新；
- **生命周期**：`onMounted`（页面加载后）、`onBeforeUnmount`（销毁前）；
- **路由**：`router/index.js` 把 URL 映射到组件；
- **Element Plus**：现成 UI 组件（表格、弹窗、日期选择）；
- **ECharts**：图表库（折线、柱状、甘特）。

## 3. 领域知识：工艺与计划到底在管什么

### 3.1 工序模板 vs 工艺路线（菜谱 vs 菜单）

- **工序模板**：一道工序的“标准做法”，例如“粗车：0.5 小时/件，需要车床”；
- **工艺路线**：一个零件的“菜单顺序”，例如法兰盘 A：下料 → 粗车 → 精车 → 钻孔 → 检验。

为什么分开？

1. 很多零件复用同一道工序（都要粗车），改标准工时就改模板一次；
2. 路线可以按零件微调（某些零件需要铣槽，有些不需要）。

### 3.2 BOM：做一件产品要多少料

```
法兰盘 A 的 BOM：
  物料 MT-45（45 号钢），单件用量 2.5 kg，损耗率 5%
```

齐套计算：

```
做 60 件需要 = 60 × 2.5 × (1 + 5%) = 157.5 kg
```

### 3.3 换型：设备换产品要调机

设备从做 A 换成做 B，要换夹具、调程序、试切，花的时间叫**换型时间**。项目里是 6×6 矩阵（30 对，有方向）。排产时如果设备上一件做的是 A、下一件做 B，就要加换型时间；**换型不算在单件标准工时里**。

### 3.4 订单 → MPS → 工单 → 工序 → 报工

| 层级 | 谁生成 | 含义 | 例子 |
|---|---|---|---|
| 销售订单 | 销售/计划员 | 客户要什么 | SO202611-0001，60 件，11-30 |
| MPS | 计划员 | 一段时间各产品做多少 | MPS202611-01 |
| 工单 | 排产 | 下到车间的任务 | WO202611-0001，60 件 |
| 工单工序 | 排产 | 工单拆成工序 | 下料、粗车… |
| 报工 | 工人 | 实际做了多少 | 粗车完成 60，不良 1 |

### 3.5 编码规则（人能看懂的身份证）

| 对象 | 规则 | 例 |
|---|---|---|
| 工序模板 | PT-序号 | PT-001 |
| 工艺路线 | PR-产品编码-V版本 | PR-PF-PL-001-V1 |
| BOM | BM-产品编码-V版本 | BM-PF-PL-001-V1 |
| 销售订单 | SO年月-序号 | SO202611-0001 |
| MPS | MPS年月-序号 | MPS202611-01 |
| 工单 | WO年月-序号 | WO202611-0001 |
| 排产方案 | SP年月日-序号 | SP20261115-001 |

### 3.6 状态机：状态不能乱跳

```
订单：草稿 → 已确认 → 已排产 → 生产中 → 已发货 → 关闭
                  ↘ 取消（草稿/已确认/已排产可取消）

工单：草稿 / 已排产 → 已下达 → 生产中 → 已完工
工序：待开始 → 已派工 → 加工中 → 已完成
```

非法跳转返回 12017。状态机的作用：防止“已发货的订单被重新排产”“已完工工序又开工”等数据混乱。

### 3.7 几个容易混淆的口径

| 口径 | 说明 |
|---|---|
| 不占设备工序 | 下料/检验在 8 台设备里没有对应设备，`is_equipment_free=True`，排产只占时间 |
| 优先级 | 1 最高（断料/停线），2 当班必到，3 默认，4 可顺延，5 有空再做 |
| 工位 | 设备绑工位（ST-…），工位绑 AGV 装卸点（N…） |
| 标准工时 | 单件加工时间（小时/件），不含换型 |
| 换型时间 | 设备换产品要的分钟数，来自换型矩阵 |
| 瓶颈 | 磨削只有 6# 磨床（2.5 件/h）、滚齿只有 4# 加工中心（1.8 件/h） |

## 4. 数据模型：把故事画成表关系

```
Product（产品，A 维护）
  ├── ProcessRoute（路线）──< RouteStep（工序）>── ProcessTemplate（模板）
  ├── Bom（BOM）──< BomItem >── Material（物料）
  ├── OrderItem（订单明细）── SalesOrder（订单）
  ├── MpsDetail（MPS 明细）── Mps（主生产计划）
  ├── WorkOrder（工单）──< WorkOrderOperation（工单工序）>── Equipment（设备）
  └── DemandForecast（预测）

ChangeoverMatrix（换型矩阵）：from_product → to_product
SchedulePlan（方案）──< SchedulePlanDetail（时间条）>── WorkOrderOperation
EmployeeSkill（员工技能）：user + step_type
```

**读法**：`A ──< B` 表示一对多（一条 A 对应多条 B）。例如一条路线对应多道工序。

## 5. 一次“运行排产”的完整链路（把前面全串起来）

页面点“运行排产”：

```
1. Vue 页面 ScheduleGantt.vue：runSchedule({mps_id: 1, start_at: '2026-11-16T08:00:00+08:00'})
2. axios POST /api/v1/planning/schedule-plans/run/
3. urls.py → SchedulePlanViewSet.run()
4. services.run_schedule(mps_id, ...)
   4.1 查 MPS 明细
   4.2 查每个产品的生效工艺路线
   4.3 查设备能力表，得到“哪台设备能做哪道工序”
   4.4 查换型矩阵
   4.5 按交期/优先级排序，逐工单、逐工序贪心排时间
   4.6 写 pl_work_order / pl_work_order_operation / pl_schedule_plan(_detail)
   4.7 计算 KPI（makespan、准时率、设备负荷）
5. Serializer 返回方案 JSON
6. 页面再调 gantt 接口拿时间条，用 ECharts 画出来
```

**理解这条链路，比背任何结论都重要。**

### 6.3 读代码的方法（重要）

1. 从页面找到接口 URL（`src/api/*.js`）；
2. 从 URL 找到 `urls.py` 和 View；
3. 从 View 找到 `services.py` 的函数；
4. 在 service 里从第一行读到最后一行；
5. 回到 models 看字段含义；
6. 最后看 tests，确认输入输出。
