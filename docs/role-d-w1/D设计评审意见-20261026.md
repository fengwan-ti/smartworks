### P0-2 `step_type` 的取值没人定义 ← 这是最硬的一处

**现在四个人的说明书、工作包、契约里都没有这个枚举值。** 按「状态值必须统一取值，不许自造同义状态」的规矩，这属于硬缺口——不定，B 写「粗车」、我写「rough_turning」、A 写「rough-turn」，W2 联调时必炸。

### P0-3 路网节点编号规则与坐标系（我的 T0，也是最晚的一个对接点）

工作包 8.1 写明「路网表由你建，A 只读，**W1 必须与 A 定死，晚定必返工**」。这件事不归 A 单方面定，需要当场拍。

**建议**（可以直接拿这套去问 A）：

1. **编号**：`N001`~`N0xx`，三位数字，按「先 y 后 x」扫格顺序编，不用业务含义编（通道/装卸点/充电位放在 `type` 里，不放进编号）。
2. **坐标系**：车间坐标系，单位 **毫米**，原点设在原料仓左下角，x 向东、y 向北。前端 ECharts 直接显示这个坐标（缩放即可，不做换算）。
3. **比例**：先按 25 节点 / 35 边的拓扑图纸量取坐标，允许 ±100 mm 误差，第一代不追求几何精度。
4. **距离口径**：`lg_road_edge.distance` 存**沿路长度**（不是直线欧氏距离）。只有「可以直穿」的两节点之间才连边。
5. **距离矩阵口径**：N×N，对角线 0，不可达填 `null`（**不填 -1、不填 999999**，否则调度算法会把不可达当成"很远"直接选中）。

第 5 条尤其要说清楚：A 的任务 3 和我的任务 1/2 共用同一个矩阵函数，这里口径不一致，两边结果会对不上。

（详见 `02-契约补丁-D.md` 第一节，可以直接贴进契约）

### P0-4 成品仓到底谁建表：`inventory` 应用里两套模型文件会打架

工作包 3.1：C 管 `inventory（原料仓）`，D 管 `inventory 中成品仓部分`。
工作包 2.2：`backend/apps/inventory/` = 仓库、库位、批次、入库、出库、库存台账、盘点 —— 归属写的是 C。

但 Django 的 `apps/inventory/models.py` **只有一个文件**。两个人同时改同一个文件，`makemigrations` 会互相覆盖，这是最容易出事的地方。

我的任务表备注其实已经写了「**复用 C 的表，不要重造**」。所以我的意见是：

| 做法 | 说明 |
|---|---|
| 表只建一次 | `Warehouse` / `Location` / `Batch` / `StockTransaction` 由 **C 建**，我直接外键引用 |
| 我只加两张 | `in_finished_inbound`（成品入库单）、`in_shipment`（发货出库单） |
| 不物理分文件 | 我把这两张追加写到 `models.py` **末尾**，并在文件里用注释标出「D 负责区间」 |
| 唯一约束 | C 在 `Location.area` 或 `type` 上预留「成品区 / 发货口」两个取值，我需要用 |

**风险**：同一个文件两个人改，git 冲突会有。W2 起建议改成 `apps/inventory/models_warehouse.py` / `models_finished.py` 两个文件、`models.py` 里 `from .models_xxx import *`。**这条要不要改，请 A 拍一下**——现在改成本最低，W2 之后改要动迁移。

**这条如果你觉得没问题，我 W1 就把两张表的结构写出来发给 C 过一遍。**

## 二、P1（W1 内定）

### P1-1 建议 1/2/3 拆开的时间点：`agv_path` 写权限太暧昧

契约 2.10 里 `/logistics/agv-paths/plan/` 是「任务 3 路径规划」，负责人列的是 A（第三节速查表）。
但 workpackage 8.2 写 `lg_agv_path`「**由 A 写入**」——也就是 A 往我的应用里写数据，A 自己的 `apps/` 下没有这张表。

**建议**：
- 表建在我这里（`apps/logistics/models.py`），A 只调用我提供的 `services.record_agv_path(...)`，不直接写 ORM；
- 或者干脆由**我**提供 `POST /logistics/agv-paths/plan/` 的接口壳子（入参出参按契约），A 只实现里面的 `find_shortest_path()` 函数，塞进 `apps/algorithms/scheduling/path/`。

第二种更干净，也不会出现「A 改我的 models」。**但这样任务 3 的归属就模糊了，代码是我写的、算法是 A 写的——个人贡献这项怕不好算。**

→ 我的意见是**选第一种**：A 写算法函数 + 我写接口，但**接口归属列在 A 名下、A 自己提 PR 到我这个文件**，提交记录是 A 的，个人贡献的账很清楚。

### P1-2 距离矩阵接口一会儿是两个、一会儿是一个

- 契约 2.10 第 123 条：`GET /logistics/road-network/distance-matrix/`
- 我的任务表 W2：距离矩阵函数，「A 的路径规划能直接调」
- 工作包 8.2：同一个函数，只写一份

**建议**：做成两件东西——
1. `apps/logistics/services.py` 里一个纯函数 `build_distance_matrix()`，**不碰数据库也能算**（传路网对象进去），A 在算法里直接 import 用；
2. 对外一个 `GET /logistics/road-network/distance-matrix/`，出参 `{"node_ids": [...], "matrix": [[...]]}`。

这样 A 不用走 HTTP，我也不用担心接口还没上线。

### P1-3 「搬运任务生成」契约里和说明书对不上

| 来源 | 说法 |
|---|---|
| 契约 2.10 | `/logistics/transport-tasks/` 只有 **GET**（第 124 条） |
| 契约 2.11 | `/transport-tasks/from-outbound/`、`/from-operation/` 是 **POST** |
| 产品说明书 5.11 | 「搬运任务生成：由领料/转序/入库事件**自动生成**任务」 |

## 四、我认为设计上**明确没问题、不用改**的（省得大家纠结）

- **算法包重组**（7 项任务并成 5 个包）——合理，反而是对的，它把「共用预处理链路」这件事显性化了。
- **第一代不做 Docker / CI / Celery**——对，四个新手 + 8 周，这些都会变成黑洞。
- **不接真实硬件、模拟器顶感知层**——对，而且 `DataSource` 抽象层这个预留是真的有用，答辩能讲。
- **批次级追溯不做单件级**——对。
- **把 `F5 排产可解释性`、`F6 What-if` 提到「可选加做」**——我保留意见：这两项对创新性评分有帮助，但**不该在第一版的二三周里做**。你说的「两三周做第一版、后续加功能」正好对上——这两项放第二版最合适，别在 W1~W3 碰。
- **13 岗位全可登录、7 个核心做深**——对。13 个都做深，8 周做不完。
